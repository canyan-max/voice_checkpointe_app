# USB 固件升级：APP 与 Boot 交接记录

记录日期：2026-11-27。本文记录当前已验证的基线、下一步设计和待办。当前固件只完成暂存和安装判断，尚不会安装固件。

## 1. 当前进度

| 环节 | 当前行为 | 验证情况 |
| --- | --- | --- |
| USB → QSPI | APP 识别 FAT32 U 盘后，按 SW2 将 `1:/UPDATE.BIN` 分块写入 QSPI。按源文件与 QSPI 回读的 CRC32 核对，成功后写入待安装记录。 | 实板通过。早期曾导出 `READBACK.BIN` 用电脑按字节比对；现已移除导出，保留回读校验。 |
| Boot QSPI 检查 | 先探测 JEDEC 和状态，再只读检查待安装记录。没有有效提交标记时跳过整包；有标记时检查长度、目标地址、向量和 CRC32，同时与板上 APP 逐字节比较。 | 实板已见 `no request`、`same image, skip` 和 `copy needed (check only)`。坏包及读失败路径在主机模拟中覆盖。 |
| Boot → APP | Boot 使用复位时钟，只初始化检查和日志所需的外设。跳转前停 SysTick、清挂起、切换 VTOR/MSP，再进入 APP 的复位入口。APP 在 `main()` 的用户区重设 VTOR。 | 实板通过；APP 日志、播放、QSPI 配置读取及 USB 重新就绪正常。 |
| 内部 Flash | 曾手动触发尾部 2 KiB 扇区擦写、自检读回和恢复空白。正式升级判断仍是只读，当前不会擦写 APP 区，也不会清待安装标记。 | Bank 2 尾扇区实板通过；正式 APP 区、Bank 1 擦写、跨 Bank 和断电恢复尚未验证。 |

最近实板记录：

- 同版暂存：`285792` 字节，CRC32 `B9781E1E`，USB 暂存并校验用时 `6209 ms`；Boot 打印 `BOOT OTA same image, skip`，随后 APP 正常启动。
- 异版暂存：`285712` 字节，CRC32 `8E272880`，USB 暂存并校验用时 `6202 ms`；Boot 打印 `BOOT OTA copy needed (check only)`，随后仍启动板上的旧 APP。
- 异版冷启动检查：Boot 的 CRC32 由逐位计算改成 64 字节查表后，检查用时从 `9514 ms` 降到 `3119 ms`，准备跳转时间为 `3122 ms`。当前标记不清，所以复位后会重复检查；这不是正常无更新启动应有的耗时。

## 2. 两侧共用约定

| 区域 | 地址（末地址包含） | 用途 |
| --- | --- | --- |
| 内部 Flash：Boot | `0x08000000–0x08007FFF` | 32 KiB，Boot 链接上限。 |
| 内部 Flash：APP | `0x08008000–0x080FF7FF` | 990 KiB，Keil IROM1 Size 为 `0x000F7800`。 |
| 内部 Flash：自检 | `0x080FF800–0x080FFFFF` | 2 KiB，暂保留；不在正式安装范围内。 |
| QSPI：LittleFS | `0x00000000–0x00DFFFFF` | 14 MiB，存放现有配置。 |
| QSPI：升级元数据 | `0x00E00000–0x00E00FFF` | 4 KiB，独立扇区。 |
| QSPI：暂存镜像 | `0x00E01000–0x00FFFFFF` | 物理暂存区；当前镜像大小仍受内部 APP 容量限制。 |

当前元数据 V1 是 4 个 32 位小端字段，从 `0x00E00000` 起：

| 偏移 | 字段 |
| --- | --- |
| `0x00` | 镜像字节数 |
| `0x04` | 镜像 CRC32 |
| `0x08` | 目标地址，必须为 `0x08008000` |
| `0x0C` | 提交标记 `0x3141544F`，前三个字段写入并回读成功后才写 |

APP 在暂存前先擦旧元数据；镜像写完并校验成功后，才发布完整记录。升级文件是**链接到 `0x08008000` 的 APP 生成的原始 BIN**，改名为 `UPDATE.BIN`；烧录器下载用各自的 HEX。两工程地址约定分别在各自的 `00_Project_Config/board_storage_layout.h`，改动时要一起核对。

## 3. 下一步方案（未实现）

**APP 负责准备升级包，Boot 负责决定并执行安装。** USB、TF、RS485 将来只负责提供输入数据，复用同一套 APP 暂存流程。LittleFS 和 OTA 共用现有 QSPI 锁；本阶段不新增存储任务。

| Boot 的判断 | 下一步动作 |
| --- | --- |
| 没有待安装请求，也没有安装中状态 | 只读元数据并检查现有 APP 向量，然后跳转。不要读整份 QSPI 镜像。 |
| 有请求，已确认字段或镜像无效，且还没擦过 APP | 清掉请求，再启动现有 APP，避免下次开机重扫同一坏包。 |
| 有请求，镜像有效，与内部 APP 完全一致 | 清掉请求，启动现有 APP。 |
| 有请求，镜像有效，与内部 APP 不同 | 完整校验通过后，先持久化并确认「安装已开始」，再擦写 APP 区。写完从内部 Flash 回读校验，通过后才能清标记并跳转。 |
| QSPI 读超时或设备读失败 | 不把读失败当成 CRC 错误。尚未开始擦写时保留请求，可跳现有 APP；安装已开始时不能跳到可能只写了一半的 APP。 |
| 安装途中断电、擦写失败或内部回读不匹配 | 保留安装状态，下次从已验证的暂存镜像重新安装。暂存镜像不可用时留在 Boot。 |

「安装已开始」建议用独立状态字段，先定编码和写入顺序，再改两侧代码。至少要保证：第一次擦 APP 之前，状态已经写入并回读确认；安装后内部回读成功之前不得擦状态；无法明确判断是否开始过安装时，不把一个看起来合理的向量表当成 APP 完整的证据。旧 V1 记录能否沿用、状态写到一半怎么判定、用擦除还是写失效值来消费请求，都需要在实现前确认。

## 4. 待办顺序

- [ ] **先定元数据状态表**：空、待安装、安装已开始、已消费/无效；约定 V1 兼容、NOR 位写入方向、写到一半的判定，以及清标记失败后的处理。
- [ ] **先测只读及清标记分支**：无请求直接启动、同版清标记、坏包清标记，下一次冷上电不要重扫；QSPI 读失败时保留请求。先不擦 APP。
- [ ] **再接正式擦写**：复用厂商内部 Flash 擦写接口；在 Boot 侧限制 APP 地址范围与扇区边界，验证 Bank 1 和跨 Bank，覆盖最后不足一个字的写入及内部回读。Boot 和尾部自检区都不能被擦到。
- [ ] **断电恢复实测**：至少覆盖标记发布前、第一次擦 APP 后、写入中、内部校验成功但尚未清标记。每个阶段检查日志、是否重试及是否误跳转。
- [ ] **完成验证后收尾**：记录无请求冷启动耗时和一次完整安装耗时，建立 APP/Boot 配套版本；再决定是否删除自检、回收尾部 2 KiB。TF 和 RS485 后续接入，4G 暂缓。
